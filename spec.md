# Cassis Order Protocol v1.0

A JSON-based protocol for streaming an order page from a merchant to a customer's wallet, and getting paid (or paying back) at the end of it.

**Version:** 1.0 · **Status:** Draft

## Introduction

The Cassis Order Protocol (COP) is built on **[hypereffect](https://hypereffect.dev)**, a small protocol for server-driven UI. A **server** streams an order page to a **client** as hypereffect messages, the client draws it with its own native components and reports back what the user does, and money moves through invoices.

Everything about the page itself — framing, sessions, components, signals, expressions, handlers and actions — is hypereffect, unchanged. This document defines only what COP adds:

- The transport: an **iroh** connection, found through a [connection URI](#connection-uri) that is usually scanned from a QR code, or through an [HTTPS web address](#web-addresses) that publishes one (see [Transport](#transport)).
- Two messages for money, neither of them a component: `invoice`, which asks the client to pay, and `invoicerequest`, which offers the client money and asks it to issue an invoice for it.
- What the hypereffect `hello` carries, and so how a flow is opened and how it is found again later: `params`, the parameters from the connection URI; `session`, a string generated by the client and always sent; and `force_resume`, which asks the server to reopen that session or say it cannot. See [Transport](#transport) and [Sessions](#sessions).
- One reason for the hypereffect `close` message, `session_not_found`, with which a server refuses to reopen a session it does not know.
- One member of the hypereffect `metadata`, `mode`, which tells the client whether the connection URI it came from may start another flow.

Where hypereffect says "renderer," this document says **client**.

### Roles

- The **server** is the merchant's side: a shop, a restaurant, a vending machine, a person selling something — anyone who hosts an order endpoint. "Server" describes the role, not the hardware: it may be an always-on machine, or the merchant's own phone. It describes the UI, reacts to the client's actions, and sends invoices.
- The **client** is the payer's side: a wallet app, usually on the payer's phone. It scans the server's QR code or opens its web address, opens the connection, draws the order page with its own native components, sends the payer's actions back, and shows its own payment screen when it receives an invoice.

The client always opens the connection. The server cannot reach a client on its own.

## Example: a pizza ordering flow

Before the details, here is a complete exchange between a client and a server: a small pizza order that ends in a payment.

1. The payer scans a QR code on a flyer. The client opens an iroh connection to the server named in it, and sends a `hello` with the parameters from the QR code and a freshly generated `session` string for this order, so the payer can come back to it later.
2. The server sends a pizza menu.
3. The payer taps a pizza. The client sends an `action` to the server.
4. The server updates the page: the chosen pizza, and a choice of extra topping (or none).
5. The payer picks a topping. The client sends another `action`.
6. The server rewrites the page: the order summary, a delivery address field, and a pay button.
7. The payer types the address and taps the pay button. The client sends an `action` carrying the address.
8. The server sends an `invoice`. The client shows its own payment screen for it, and the payer pays.

Every message is one line: a tag, a space, and a JSON object, as defined by hypereffect.

### 1–2. Client connects, server sends the menu

The QR code on the flyer holds a [connection URI](#connection-uri):

```
cop://5f1c9d0a27e4b6c38d2f71a09e4b5c6d8a3f2e1b0c9d8e7f6a5b4c3d2e1f0a9b#name=Luigi%27s%20Pizza
```

The client connects to the iroh endpoint in it and sends its `hello`, with the parameters from the URI (here, `name`) and a `session` string it just generated for this order.

```
hello {"params":{"name":"Luigi's Pizza"},"session":"f1K9xQ2v8Tn4LmZp7Rb3wq"}
```

The server says who it is, then answers with the menu:

```
metadata {"name":"Luigi's Pizza","description":"Wood-fired pizza, Via Roma 12"}
element {"id":"title","type":"text","variant":"h1","text":"Choose your pizza"}
element {"id":"menu","type":"list"}
element {"id":"margherita","type":"button","parent":"menu","label":"Margherita — $8.50","onPress":{"action":"selectPizza","payload":{"pizza":"margherita"}}}
element {"id":"pepperoni","type":"button","parent":"menu","label":"Pepperoni — $10.00","onPress":{"action":"selectPizza","payload":{"pizza":"pepperoni"}}}
element {"id":"funghi","type":"button","parent":"menu","label":"Funghi — $9.50","onPress":{"action":"selectPizza","payload":{"pizza":"funghi"}}}
```

The payloads carry only *what* was chosen, not its price. The server looks prices up itself; see [Security considerations](#security-considerations).

### 3. Payer picks a pizza; client notifies the server

```
action {"name":"selectPizza","payload":{"pizza":"pepperoni"},"signals":{}}
```

### 4. Server updates the page: selected pizza + topping choice

```
remove {"id":"menu"}
element {"id":"title","type":"text","variant":"h1","text":"Your order"}
element {"id":"selected","type":"text","text":"Pepperoni pizza — $10.00"}
element {"id":"toppings","type":"card","title":"Add an extra topping?"}
element {"id":"topping_row","type":"row","parent":"toppings"}
element {"id":"olives","type":"button","parent":"topping_row","label":"Olives (+$1.00)","onPress":{"action":"selectTopping","payload":{"topping":"olives"}}}
element {"id":"chili","type":"button","parent":"topping_row","label":"Chili (+$0.75)","onPress":{"action":"selectTopping","payload":{"topping":"chili"}}}
element {"id":"skip","type":"button","parent":"topping_row","variant":"plain","label":"No extra topping","onPress":{"action":"selectTopping","payload":{"topping":null}}}
```

### 5. Payer picks a topping; client notifies the server

```
action {"name":"selectTopping","payload":{"topping":"chili"},"signals":{}}
```

### 6. Server rewrites the page: order summary, address, pay button

```
remove {"id":"toppings"}
signal {"order":{"address":""}}
element {"id":"title","type":"text","variant":"h1","text":"Where should we deliver?"}
element {"id":"selected","type":"text","text":"Pepperoni pizza + chili — $10.75"}
element {"id":"address","type":"input","label":"Delivery address","bind":"order.address"}
element {"id":"pay","type":"button","variant":"primary","label":"Pay $10.75","disabled":{"cel":"s.order.address == ''"},"onPress":{"action":"pay"}}
```

The address field is bound to the `order.address` signal. Typing into it updates the client's signals and sends nothing; the pay button stays disabled while the address is empty.

The pay button is an ordinary `button`. Nothing about it is payment-aware: hypereffect has no payment component. Tapping it only tells the server the payer is ready; the server answers with an invoice.

### 7. Payer taps the pay button; client notifies the server

```
action {"name":"pay","signals":{"order":{"address":"221B Baker St, London NW1 6XE"}}}
```

The address arrives in the action's signals. The server checks it anyway: had it been empty, the server could have answered with an updated page asking for it instead of an invoice.

### 8. Server sends the invoice

```
invoice {"invoice":{"payment_hash":"3f9a…e21c","amount_msat":10750000,"expires_at":1793875200,…},"memo":"Pepperoni + chili, to 221B Baker St"}
```

The `invoice` member is a whole Cassis invoice, abbreviated here and in the other examples.

On receiving an `invoice` the client **shows its own payment screen**, with what the invoice itself says: amount, payee, expiry. That screen belongs to the client; this protocol says nothing about what it looks like. See [`invoice`](#invoice-server-client).

The payment travels over the invoice's own settlement mechanism, and the server learns the outcome from there, not from this protocol. Once paid, the server may turn the page into a confirmation: an order number, a delivery time.

### Flows with no UI at all

The example above is the longest kind of flow, not a requirement. A flow is only a stream of messages, so a server can skip the UI entirely.

#### Paying at the till

The QR code on the till names the server and carries a `till` parameter identifying that till. The client connects, and the server, which already knows what is being bought there, sends its `metadata` and an invoice straight away. The client shows its payment screen, the payer pays, and the flow is over. No element was ever sent.

```
metadata {"name":"Luigi's Pizza","description":"Till 2"}
invoice {"invoice":{"payment_hash":"b207…41d9","amount_msat":3500000,"expires_at":1793871900,…},"memo":"1 × flat white"}
```

#### Offering the client money

The opposite direction: the server has money for the client — a refund, a cashback, a withdrawal from a prepaid balance — and asks the client to issue an invoice for it. A QR code like this is usually made for one payer and one payment, so the server marks it as [`single_use`](#messages).

```
metadata {"name":"Luigi's Pizza","description":"Refund","mode":"single_use"}
invoicerequest {"amount":24000,"networks":["liquid","cashu::mint.example.com"],"memo":"Refund for unused days"}
```

If the payer accepts, the client generates an invoice with its own keys, payable on one of those networks, and sends it back. The server pays it.

```
invoice {"invoice":{"payment_hash":"5c04…9a7e","amount_msat":24000000,"expires_at":1793872800,…}}
```

#### Reopening an order

The client reconnects with the same `session` string it used before, this time with `force_resume`, and the server shows whatever it wants to show for that order: where an unfinished order left off, a receipt for a paid one, a refund form. See [Sessions](#sessions).

```
hello {"params":{"name":"Luigi's Pizza"},"session":"f1K9xQ2v8Tn4LmZp7Rb3wq","force_resume":true}
```

If the server no longer knows that session, it says so and closes the connection:

```
close {"reason":"session_not_found"}
```

## Protocol overview

A COP flow is a hypereffect session with two extra kinds of message for money.

A typical flow (the order is not fixed):

1. **Connect:** The payer scans a [connection URI](#connection-uri) or opens a [web address](#web-addresses) that publishes one. The client connects to the server and sends a `hello` with a `session` string and the parameters from the URI.
2. **Page:** The server sends hypereffect `element`, `remove` and `signal` messages to build and update the order page. As the payer interacts, the client sends `action` messages, and the server answers with more of them.
3. **Invoice:** At any point the server may send an `invoice`, and the client shows its payment screen for it.
4. **Invoice request:** At any point the server may send an `invoicerequest` offering money, and the client may answer with an `invoice` of its own.

Step 2 is the UI half of the protocol and steps 3–4 the money half. Either may be empty. The smallest possible flow is a connection followed by a single `invoice`; see [Flows with no UI at all](#flows-with-no-ui-at-all).

## Connection URI

A server publishes its order endpoint as a URI, usually printed or displayed as a QR code: on a flyer, a table, a till, a vending machine, or the merchant's phone screen. It may also publish the URI at an HTTPS web address, which a client resolves before connecting; see [Web addresses](#web-addresses).

```
cop://<endpoint-id>[?_relay=<relay-url>][#<parameters>]
```

- `<endpoint-id>` (required): the server's iroh endpoint ID — its Ed25519 public key, as 64 lowercase hexadecimal characters. This is the only thing the client needs to reach the server and to know it is talking to the right one: iroh authenticates the connection against this key.
- `_relay` (optional, in the query): the URL of an iroh relay to reach the server through, instead of the client's default relays. A merchant who cares about privacy can run their own relay, including one reachable only over Tor: a relay URL whose host is a `.onion` address means the client must connect to it through Tor. It is the only query parameter COP defines. The underscore marks it as addressing the connection rather than the order, so it is consumed by the client and **never sent** in the `hello`. The value is percent-encoded. Other query parameters are ignored.
- `<parameters>` (optional): a list of `key=value` pairs joined by `&`, in the fragment, as in a [hyperb](https://github.com/hypereffect/hyperb/blob/master/SPEC.md#18-session-parameters) address. Keys and values are strings, percent-decoded as UTF-8, and a value may be empty. A pair without `=`, a pair with an empty key, an empty pair, a repeated key and a value that is not UTF-8 make the URI invalid. An empty fragment is the same as none. The fragment is part of the URI, not of the endpoint: the same server with other parameters is still the same server. The parameters defined by COP are:
  - `name`: a display name for the server, which the client may show before it has connected. Once the server sends its hypereffect `metadata`, that replaces it. It is not verified.

In a `cop://` URI there is no path: the endpoint ID alone selects the server. Clients must ignore parameters they do not recognise, but still send them in the `hello` (see [Transport](#transport)).

`cop://` is the only scheme COP defines for a connection URI. An HTTPS web address can also lead to one; see [Web addresses](#web-addresses). The scheme name is case-insensitive, and the endpoint ID is case-insensitive too: clients lowercase it.

**Examples:**

```
cop://5f1c9d0a27e4b6c38d2f71a09e4b5c6d8a3f2e1b0c9d8e7f6a5b4c3d2e1f0a9b
```

```
cop://5f1c9d0a27e4b6c38d2f71a09e4b5c6d8a3f2e1b0c9d8e7f6a5b4c3d2e1f0a9b#table=12&name=Luigi%27s%20Pizza
```

```
cop://5f1c9d0a27e4b6c38d2f71a09e4b5c6d8a3f2e1b0c9d8e7f6a5b4c3d2e1f0a9b?_relay=http%3A%2F%2Fexampleonionrelayaddressxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.onion#till=3
```

### Web addresses

A web address can stand wherever a `cop://` URI would: printed, shown as a QR code, or sent as a link. It may be written with or without a scheme:

```
example.com/order/123
```

```
https://example.com/order/123
```

Clients should support both. An address without a scheme gets `https://` prefixed; an `http://` address is upgraded to `https://` and never fetched over plain HTTP. The client fetches the address with `GET`, following redirects only while they stay on HTTPS, and looks in the document's `<head>` for a `link` element whose `rel` contains the token `cassis-order`:

```html
<link rel="cassis-order" href="cop://5f1c9d0a27e4b6c38d2f71a09e4b5c6d8a3f2e1b0c9d8e7f6a5b4c3d2e1f0a9b#table=12">
```

The `href` must be an absolute `cop://` URI, as defined above. The client resolves it exactly as if that URI had been scanned: its parameters are the flow's parameters, and the client adds its `session` as usual. A `link` element outside the `<head>`, a malformed link, and a link that does not point to `cop://` are all ignored; the first valid one wins. A response that is not HTML, or a page with no valid link, does not resolve to a flow.

The page is only a way to publish the URI. The client must not render it, run its scripts, or follow links from it, and the server is still authenticated by the iroh endpoint ID in the resolved URI, not by the web address. The web address's own query and fragment are not COP parameters: the flow's parameters come only from the resolved `cop://` URI.

Fetching the page reveals the payer's IP address to the web server. Clients should bound the fetch — a small maximum size, a short timeout, and a limited number of redirects — and should not resolve a web address that the payer did not explicitly choose. See [Security considerations](#security-considerations).

## Transport

A single transport is defined: an **iroh** connection using the ALPN `cassis-order`.

- The **client** always initiates. It dials the endpoint ID from the connection URI with the ALPN `cassis-order`, through the URI's `_relay` query parameter if one is given. iroh authenticates both ends: the client knows which server it reached, and the server learns the client's endpoint ID (see [Sessions](#sessions)).
- The client opens one bidirectional stream on the connection. Everything in the flow travels over that stream, in both directions, as hypereffect lines written directly to the stream.
- The **first line** the client sends is the hypereffect `hello`. hypereffect leaves the members of its object to the protocols built on it; COP defines these:
  - `params` (object, optional): the fragment parameters of the connection URI, as strings, percent-decoded. It is the `params` member that [hyperb defines](https://github.com/hypereffect/hyperb/blob/master/SPEC.md#18-session-parameters), with its rules: it is omitted when the URI has no parameters, and a server treats a `params` that is not an object of strings as no parameters. The client sends them once, here, and never again.
  - `session` (string, required): a random string that names this flow, generated by the client and always sent. A client that resumes an earlier session reuses the string it kept from before. A `hello` without a non-empty string `session` is not a COP flow, and the server may close the connection. See [Sessions](#sessions).
  - `force_resume` (boolean, optional): `true` asks the server to reopen the session named by `session`, and to refuse if it cannot, rather than decide for itself. Any other value, or none, leaves that to the server. See [Resuming a session](#resuming-a-session).

  Servers ignore other members.
- The flow ends when either side closes the connection. A server that ends it with a reason the client should know sends the hypereffect `close` message first; the only reason COP defines is `session_not_found` (see [Resuming a session](#resuming-a-session)).

**Example `hello` lines:**

```
hello {"session":"f1K9xQ2v8Tn4LmZp7Rb3wq"}
```

```
hello {"params":{"table":"12","name":"Luigi's Pizza"},"session":"f1K9xQ2v8Tn4LmZp7Rb3wq"}
```

```
hello {"params":{"table":"12","name":"Luigi's Pizza"},"session":"f1K9xQ2v8Tn4LmZp7Rb3wq","force_resume":true}
```

## Sessions

Every flow is one conversation about one thing: an order, a bill, a membership. Payers like to be able to come back to it, so every `hello` names its session.

- The **`session`** member of the `hello` is generated by the **client** and always sent. It is a random string that names *this* flow at this server. The client generates a fresh one for a new flow, or reuses one it kept from a past flow to continue that same session. The server uses it to tell flows apart and to find one again; the client only generates it and sends it.
- The **`params`** are the ones that came with the connection URI. The client sends them again every time, including when it resumes a session, if the original URI carried them.

**The server also sees the client's iroh endpoint ID.** iroh authenticates both ends of a connection, so the server learns the endpoint ID — the public key — of the client that connected, whether or not the flow resumes a session. That is separate from `session`: the session string names one flow, while the endpoint ID identifies the wallet, or whichever identity the wallet chose to present. What it means is the wallet's choice:

- a wallet can generate a new iroh key for every flow, so two flows cannot be linked to the same payer;
- it can keep one key per server or service, so that this server recognises the payer across flows while other servers cannot;
- or it can use a single permanent key everywhere, making the payer recognisable to every server it connects to.

**Servers cannot assume the endpoint ID is stable.** Because rotating keys is the wallet's choice, the same payer may arrive with a different key next time. A server may use the endpoint ID as a hint — to recognise a returning payer, or to rate-limit connections — but not as the payer's account or identity.

**Clients must generate long, random `session` values: at least 128 bits of randomness.** The session string is a bearer token for the flow: whoever presents it can reopen the session and see what the server shows for it. Short, sequential, or human-readable identifiers do not qualify.

**The client keeps a record of its sessions.** For each one it stores the server's endpoint ID and relay, the connection URI's parameters, the `session` string, and the invoices it paid or issued in that flow. This is the payer's own record, and it is how the payer reopens a flow later: the client connects again with the same `session` and the same parameters, and with `force_resume` (see [Resuming a session](#resuming-a-session)).

**What the server shows on a reopened flow is up to the server.** A reconnection is a new connection: it starts with an empty page until the server sends one. The server may:

- pick an unfinished order up where it left off;
- show a paid order's details — a receipt, an order number to quote, a delivery time — or a form for requesting a refund;
- show whatever else it thinks is worth showing.

**Reusing a connection URI is not resuming a session.** Opening a connection URI again, with a fresh `session`, starts a new flow: a flyer or a table's QR code is meant to be scanned again and again, by the same payer or by anyone else. Reconnecting with a `session` the client kept continues an old flow. A server can send a [`mode`](#messages) of `single_use` in its `metadata`, meaning the URI should not start a new flow again; that never stops the client from resuming the session it already has.

**Servers are allowed to forget.** For a tip jar or a coffee, the server may keep no record at all, and treat every connection as a brand-new flow. A business that expects payers to come back for receipts, refunds or another month of service will want to remember, at least for a while. How long a server remembers is policy, not wire format.

### Resuming a session

What the server does with a `session` depends on whether the `hello` has `"force_resume":true`.

**Without `force_resume`**, it is the server's choice. It may recover the existing session with that string, if it knows one, or treat the flow as a new one, whether or not it has seen the string before. The client cannot tell which it got except from the page the server sends.

**With `"force_resume":true`**, the server must not start a new flow:

- If the server knows the session, it must resume it: the flow continues that session, with whatever the server chooses to show for it (see above).
- If it does not know the session — it never saw that string, or it has forgotten it — it must send the hypereffect [`close`](https://hypereffect.dev/spec.html#msg-close) message with the reason `session_not_found`, send nothing else, and close the connection:

  ```
  close {"reason":"session_not_found"}
  ```

A client should send `force_resume` whenever it reopens a session from its record, including when the payer opens a `single_use` URI again, so that it never shows a fresh flow in place of the one the payer meant to reopen. It omits it for a new flow, with a fresh `session`. When a resume ends with `session_not_found`, the client tells the payer that the server no longer has that flow; its own record of the session, and of the invoices in it, stays as it was.

## Messages

The page is built with the messages [hypereffect](https://hypereffect.dev) defines: `element`, `remove` and `signal` from the server, `hello` and `action` from the client. The server may also end a flow with the hypereffect `close` message, whose only reason in COP is `session_not_found` (see [Resuming a session](#resuming-a-session)). COP adds the following, framed the same way:

| Tag              | Direction       |
| ---------------- | --------------- |
| `invoice`        | server → client |
| `invoicerequest` | server → client |
| `invoice`        | client → server, only in answer to an `invoicerequest` |

A plain hypereffect renderer ignores these tags; a COP client must implement them. A message missing a required member is ignored, as hypereffect does with any invalid message.

Money never enters a flow through the page. There is no payment component; a pay button is just a `button` whose handler sends an `action`, and the server answers it with an `invoice`.

### `metadata` (server → client)

The hypereffect `metadata` message, which says who the server is (`name`, `description`, `icon`). COP adds one member to it:

- `mode` (string, optional): how the connection URI that opened this flow may be used, when it is not the default. With no `mode`, the URI is reusable: it may start any number of flows, for the same payer or anyone else, like a QR code printed on a flyer or a table. The only value COP defines is:
  - `single_use`: the URI is meant to start one flow. A QR code made for one payer and one payment — a withdrawal or refund voucher, an invoice shown on a till's screen for the purchase in front of it — is single use.

  A client ignores a value it does not recognise, as if no `mode` had been sent.

A client that receives `"mode":"single_use"` keeps the session as usual, and may still resume it with its `session` string (see [Sessions](#sessions)). What it should not do is start a **new** flow from that URI: it should not offer the URI as a place to go back to, as it may for a reusable one, and if the payer scans or opens it again it should resume the session it already has for it rather than generate a new `session`, or tell the payer the code was already used.

`mode` is a hint to the client, not an enforcement mechanism. Anyone else who has the QR code can still open it with a session of their own, so a server that must pay out only once has to enforce that itself.

**Example:**

```
metadata {"name":"Luigi's Pizza","description":"Refund for order 2f8c","mode":"single_use"}
```

### `invoice` (server → client)

Asks the client to pay a **Cassis invoice**. It carries no UI of its own: the client shows **its own payment screen** with what the invoice says — amount, payee, expiry, description. What that screen looks like (a sheet, a modal, a full-screen takeover) is up to the client and out of scope for this protocol.

The payer may pay, or dismiss the payment screen. A dismissed invoice stays with the flow, so the payer can still pay it while the flow is open, and finds it in the client's record afterwards.

An `invoice` may be sent at any point in a flow, including when the page is empty. A later `invoice` replaces an earlier unpaid one: an order whose price changes, or a bill that grows, is handled by sending a new invoice.

**Members:**

- `invoice` (object, required): The Cassis invoice, as the JSON object the Cassis protocol defines. COP never looks inside it; the client hands it to its payment subsystem.
- `memo` (string, optional): A short note to show alongside the payment, e.g. `"Table 12, second round"`. The client may ignore it. Amount and payee always come from the invoice itself, never from the memo or from the page.

**Example:**

```
invoice {"invoice":{"payment_hash":"3f9a…e21c","amount_msat":10750000,"expires_at":1793875200,…},"memo":"Pepperoni + chili"}
```

The invoice is not an element and is not stored in the signals. Settlement happens through the invoice's own mechanism; a server that wants to know whether it was paid finds out from there, not through this protocol.

### `invoicerequest` (server → client)

The reverse direction of money: the server **offers the client money**, and asks it to issue an invoice for it. This is how a server refunds an order, pays a cashback, or lets the payer withdraw a prepaid balance.

**Members:**

- `amount` (integer, required): The amount offered, in sats. Cassis invoices count in millisats, so the invoice the client generates is for `amount × 1000` msat.
- `networks` (array of strings, required, not empty): The Cassis network ids the server can pay from, e.g. `"liquid"` or `"cashu::mint.example.com"`.
- `memo` (string, optional): A description to show to the payer and embed in the generated invoice, e.g. `"Refund for order 2f8c"`.
- `expiresIn` (integer, optional): The number of seconds after which the generated invoice should expire, e.g. `900`. The client may ignore it.

**Behavior:**

- The client shows the offer to the payer. If the payer accepts, the client generates a Cassis invoice with its own keys, payable on at least one of `networks`, and sends it back in an [`invoice`](#invoice-client-server) message. The server then pays it. A client that can receive on none of `networks` cannot accept the offer.
- If the payer declines, the client sends nothing. The server must not wait on an answer that may never come.
- Settlement of the returned invoice is out of scope for this protocol, as it is for one the server sends.
- An `invoicerequest` needs no page. A whole flow can be: connect, receive an `invoicerequest`, return an `invoice`, done.

**Example:**

```
invoicerequest {"amount":24000,"networks":["liquid","cashu::mint.example.com"],"memo":"Refund for unused days","expiresIn":900}
```

### `invoice` (client → server)

Sent in answer to an [`invoicerequest`](#invoicerequest-server-client), carrying the invoice the client generated with its own keys. The server pays it; settlement is out of scope for this protocol.

**Members:**

- `invoice` (object, required): The Cassis invoice the client created, as a JSON object.

**Example:**

```
invoice {"invoice":{"payment_hash":"5c04…9a7e","amount_msat":24000000,"expires_at":1793872800,…}}
```

## Security considerations

The security considerations of hypereffect apply. In addition:

- **Only the client's payment screen is trustworthy.** Everything on the page is drawn by the server, including text that says what something costs. The client must take the amount and payee it shows for a payment from the invoice itself, and must show its payment screen in a way the server cannot imitate with elements.
- **Opening a URL is not a way to pay.** A hypereffect button can ask the client to `open` a URL. Clients must not let such a URL start a payment, for example a `bitcoin:`, `lightning:` or `cassis:` link the wallet itself would handle: money enters a flow only through `invoice` and `invoicerequest`. Opening a web page also reveals the payer's network address, as remote images do (below).
- **A web address is only a pointer.** Fetching one reveals the payer's IP address to its host, and the page it returns can change at any time: it may point at any iroh endpoint. The endpoint ID in the resolved `cop://` URI still authenticates the connection, so the client must show that endpoint, not the web address, as the server's identity. Clients must fetch only over HTTPS, must not render the page or run its scripts, and must not resolve an address that the payer did not explicitly choose; a `link` tag injected into a page must not be able to open a payment flow.
- **Actions are payer input.** The client fills in an action's payload and signals, so a modified client can put anything there. Servers must not take prices, totals or anything else they would not accept from a stranger from them; the examples in this document send only *what* was chosen, and the server prices it.
- **The `session` string is a bearer token.** Anyone who has it can reopen the flow. Clients must generate `session` values with at least 128 bits of randomness and keep them private. Servers should not put more in a reopened session than its holder ought to see.
- **The client's endpoint ID is linkable.** iroh authenticates both ends of a connection, so every server sees the client's iroh public key. A wallet that reuses one key everywhere is linkable across every server it talks to; one key per service limits that linkability to that service; a fresh key per flow avoids it. Wallets should choose deliberately, and servers should treat the endpoint ID as a hint, not as the payer's identity.
- **Remote images leak the payer's network address.** `image` elements, and the `icon` of `metadata`, load from URLs the server chooses. Fetching them reveals the payer's IP address to whoever hosts them, even when the iroh connection itself goes through a Tor relay. Clients should let payers turn remote images off, and should not load them when the connection URI named a `.onion` `_relay`.
- **`name` is unverified.** The `name` parameter of a connection URI and the `name` in `metadata` are whatever the server says it is called. What identifies a server is its endpoint ID, and what identifies a payee is the invoice.

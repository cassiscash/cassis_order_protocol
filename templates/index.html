Pay for anything in the real world without leaving your wallet

Scan a QR code and the merchant's order page opens inside your wallet, drawn with the wallet's own buttons, lists and forms. Pick what you want, then pay on the wallet's own payment screen. The merchant needs no website, and the wallet needs no browser.

{# ---------------------- WHO IS WHO CARD ---------------------- #}
who is who

Server

The merchant's side: a shop, a restaurant, a vending machine, anyone hosting an order page. It can run on an always-on machine or on the merchant's own phone. It describes the page, reacts to what the customer does, and sends invoices.

Client

The customer's wallet, on their phone. It scans the QR code, opens the connection, draws the page with native components, and shows its own payment screen when an invoice arrives.

Connection

An iroh connection (cassis-order ALPN) carrying one JSON message per line, both ways. The QR code holds the server's iroh key and, optionally, a relay to reach it through.

{# ========================== HOW IT WORKS ========================== #}

How it works

  1. 01

    Scan

    The QR code is a cop: URI: the server's iroh key, optionally a relay, and a claim saying which table, till or flyer it came from.

  2. 02

    Connect

    The wallet dials the server and sends the claim along with a random order id it just made up, so it can find this order again later.

  3. 03

    Order

    The server sends the page as hypereffect elements and signals, and the wallet draws them natively. Taps go back as action messages, and the server answers with an updated page.

  4. 04

    Pay

    The server sends an invoice and the wallet shows its own payment screen. To give money back, the server sends an invoice request instead.

{# ============================== USES ============================== #}

What it's for

Commerce, inside the wallet

Anything a merchant can describe with text, buttons, lists and form fields can be an order page. A few of the shapes it takes:

Menus and carts

Browse what's on offer, pick options and quantities. The server keeps the running total and sends one invoice for the lot.

Open amounts

Tips, donations, top-ups: the customer types or picks the amount, and the invoice is for exactly that.

Tables and tills

One QR code per table or till, each with its own claim. The server already knows the bill: it can show it, or go straight to the invoice.

Refunds and cashback

The server offers money with an invoice request. If the customer accepts, the wallet issues an invoice with its own keys and the server pays it.

Unattended machines

A vending machine or kiosk runs the server itself. Its QR code is all a customer needs: no website or domain name behind it.

Coming back to an order

The wallet remembers each order's claim and id. Reconnect with them for a receipt, a delivery update, a refund, or another month of a membership.

{# ---------------- no browser, no website ---------------- #}

No browser in the wallet. No website for the merchant.

The wallet draws every order page with its own native components, so it looks and behaves like the rest of the wallet. The merchant needs no web server, no domain name and no certificate: an iroh key is the address, and it works from a phone.

A small set of components

The page is hypereffect: text, buttons, text fields, checkboxes, lists, rows, columns, images and a few more. Small enough for any wallet to build with its own UI toolkit.

The payment screen is the wallet's

The server can draw whatever page it likes, but not the payment screen. What you pay, and to whom, comes from the invoice, and your wallet shows it.

Bring your own relay

A merchant can name their own iroh relay in the QR code, including one that is only reachable over Tor.
